### Half Adders
![float-right|300](images/Half%20Adder.png)A half-adder is a simple circuit capable of adding two bits, producing a single-bit result as well as a single-bit carry signal. Half-adders on their own are very rare, as they can only ever add two single bits, which is generally not very useful. 

A half-adder is made using two gates:
- $S_{um}=a\oplus b$
- $C_{out} = a\wedge b$
 
### Full Adders
![float-right|200](images/Full%20Adder%201.png)A full-adder is a circuit capable of adding three bits, producing a single-bit result as well as a single-bit carry signal. Full-adders form the basis of all adders capable of adding multi-bit numbers. At its most basic, a full-adder can be considered to be two half-adders combined to allow for three inputs. The version of the full-adder circuit shown here is the most commonly cited version given in textbooks. 

![float-right|200](images/Full%20Adder%202.png)A more commonly used version, saving an AND gate is also shown. It is used as the basis for _ripple-lookahead_ adders and all multi-bit integer adders other than ripple-carry adders. It can, of course, still be used to build ripple-carry adders, though it is not required to do so.
### Ripple-Carry Adders
![float-right|300](images/Ripple-Carry%20Adder.png)A ripple-carry adder is a multi-bit integer adder, that serves as the baseline for integer addition. This type of adder is often not used beyond sizes of 8-bits as it has a very long critical path, making meeting timing constraints potentially difficult with large ripple-carry adders.
To build a ripple-carry adder, simply chain together a line of full-adders (of either design), so that the _carry out_ ($C_{out}$) of the nth-bit full adder is the _carry in_ $C_{in}$ input of the n+1th-bit full adder. The carry-in of the lowest-bit should be low.  
### Carry-Lookahead Adders (CLA)
![float-right|300](images/Full%20Adder%20PG.png)The problem with using ripple-carry adders, is that before the final-bit can even be computed, every bit before it also has to be full calculated. Instead of doing this, we can take notice of the full-adder's circuit and out of it, create two new signals: _Propagate_ ($p = A \oplus B$) and _Generate_ ($g=A\wedge B$). From these two new signals, we can see that:
$$S=P \oplus C_{in}$$
$$C_{out}=G\vee(P\wedge C_{in})$$
Conceptually, the $P$ and $G$ values are quite simple, if _generate_ is high, then that means that a carry was generated by the sum of the inputs $A$ and $B$, and if _propagate_ is high, that means that a carry would be performed if the previous bit's addition resulted in a carry. 

We can then make use of this to 'predict' whether a carry will be needed for any particular bit that we want to add, using the following formula:
$$C_k=\bigvee_{i=0}^{k-1}\left(g_i\wedge\bigwedge_{j=i}^{k-1}p_j\right)$$
While this looks scary, it is actually quite simple. For instance, if we wanted to know if the addition of four bits will have a carry, then we know that it could have a carry if:
- Bit 3 generated ($g_3$)
- Bit 2 generated, and bit 3 propagated ($g_2\wedge p_3$)
- Bit 1 generated, and bits 2 and 3 propagated ($g_1\wedge p_2\wedge p_3$)
- Bit 0 generated, and bits 1 through 3 propagated ($g_0\wedge p_1\wedge p_2\wedge p_3$)
- Carry In is high, and bits 0 through 3 propagated ($C_{in}\wedge p_0\wedge p_1\wedge p_2\wedge p_3$)
Thus, we can say that there will be a carry if any of these conditions are met:
$$C_4 = (g_3)\vee(g_2\wedge p_3)\vee(g_1\wedge p_2\wedge p_3)\vee(g_0\wedge p_1\wedge p_2\wedge p_3)\vee(C_{in}\wedge p_0\wedge p_1\wedge p_2\wedge p_3)$$
From this, we can see that the generate and propagate signals can be computed in parallel, and from them, the carry signals can be calculated in parallel. This means that we can have all of the bits of the output at the same time. Specifically, we're reducing the critical path length from being O(n), where n is the number of bits being added to O(1). Note that while the multi-input gates that are used here _are slower_ than traditional two-input gates, they are _not slower_ than the chain of two-input gates needed to perform the same operation. Typically, the delay of a multi-input gate is 1.5-3x the delay of a two-input gate, but compared to the sum of the chain of two-input gates, this is meaningfully faster.

![float-right|400](./images/Chained%20Carry%20Lookahead%20Adder.png)One major downside of this design is fan-in and fan-out. The gates needed are very, very wide and the $p$ and $g$ signals must drive many gates. This is quite difficult to do, so generally, carry-lookahead is limited to four-bit adders. As a compromise, we can instead, form a chain of smaller CLAs. This does re-introduce the need for bits to wait on other bits, but despite this, we get an O(log n) critical path, with none of the major downsides of large carry generators.
### Manchester Carry Chain
A _Manchester Carry Chain_ is conceptually similar to a _carry-lookahead adder_, however, it exploits the fact that the logic to generate the n'th carry signal includes the logic for all previous signals. Thus, it simplifies the carry generation by 'tapping off' these intermediate signals. However, while this works in TTL or nMOS logic, where OR gates are implicitly just the joining of two wires, in CMOS logic, this is not possible, so this technique is not widely used due to the prevalence of CMOS logic today.
### Carry-Bypass Adders
![float-right|400](images/Carry%20Bypass%20Adder.png)A _carry-bypass adder_ is a simpler version of a carry-lookahead adder that is no longer relevant in modern clocked designs. Instead of having complex carry prediction logic per block, it instead simply ands together all the propagate signals in a block to get a 'group propagate' signal. If this group propagate signal is high, then the carry from the previous block is forwarded straight to the next block, bypassing the block entirely. This means that after each block, a MUX is required. However, if the group propagate signal is not high, then the carry signal from the previous block goes through the current block of add-circuitry. While it would be possible for the individual blocks to be small carry-lookahead adders, they tended to be simple ripple adders.

There are several reasons why this design is not used today:
- Carry-Bypass adders are only faster than ripple adders for specific values being added that allow for block carry propagation to be bypassed. For some values, they can be slower than a ripple adder due to the muxes the carry has to flow through. However, probabilistically, a carry-bypass adder is faster.
- Because a carry-bypass adder takes a variable amount of time, in a synchronous, clocked design, the clock has to be as slow as the worst case scenario, where no blocks' carry propagation can be bypassed, to meet timing constraints. As a result, in a clocked environment, this design is _always_ slower than a ripple adder, and uses more transistors.
- In some very, very old designs, computation was performed asynchronously, with the completion of a calculation triggering a 'done' signal that triggered the next 'clock' pulse. Under this scenario, instructions can take a variable amount of time, which allows the average speedup of a carry-bypass adder to be useful.
- In theory, if it is allowed that an addition may take multiple clock cycles, where the number is simply indeterminate, then the carry-bypass adder _could_ be useful, but in practice, addition is so well optimised that it almost always takes only one cycle, and such designs are so rare as to not exist.
### Carry-Select Adders
##### Linear
![float-right|200](./images/Carry%20Select%20Individual.png)A _linear carry-select adder_ works in principle by, for each bit of the numbers being added $A_i, B_i$, computing the sum and carry for the single-bit addition of those bits for a carry in of zero and a carry in of one. Then, based on the carry out of previous bits, selecting which addition's results get used. In practice, however, this design can be optimised. Instead of performing the full addition twice, which calculates the same propagate and generate twice, we instead calculate $P_i$ and $G_i$ only once for each bit, and duplicate only the carry out for each bit ($C_{i}=G_i\vee(P_i\wedge C_{i-1})$. Then, we use this to drive the mux inputs, and selectors, with the sum generation occurring only at the end, by XOR'ing $P_i$ with the selected carry signal.

![](./images/Carry%20Select%204.png)

As can be seen in the diagram above, the critical path for any addition is through the first bit's carry propagation logic, then through all the muxes. and finally the last XOR gate. This is a significant speedup, as muxes are a common and highly optimised piece of logic, which is significantly faster than several cascaded full-adders. While this, like the other designs shown previously is still an O(n) critical path, the gain is in that the coefficient of $n$ is significantly smaller, with a similar constant term.
##### Square Root
![float-right|200](./images/Block%20Carry%20Select.png)One way to improve on the linear carry-select adder is by instead of selecting the carry on each bit, instead using a more brute-force method to allow for blocks of several bits to be selected. To implement this, for each block there are two ripple-carry adders. One for if the whole block had a carry in of one, and one for zero. Then, the sum and final carry out of these ripple adders are selected between based off the previous block's carry out. A single 2-input block is shown right. What makes this truly a 'square root' carry-select adder is the careful control of the sizes of the blocks. By chaining blocks of linearly increasing width, we can balance how much work each block has to do with the time the carry chain takes to get there - later blocks have to go through several muxes, so they have more time, so can compute larger groups of bits and still be ready in time.

![](images/20%20Bit%20Square%20Root%20Carry%20Select%20Adder.png)

By using this pattern, we can get the critical path to be O(sqrt(n)) which is not just better than the other options, it's _asymptotically better_, which means the improvement gets better and better the larger the adder we need! Specifically, the critical path is _either_ the time taken for the largest (final) block to ripple all the way through, _or_ the time for the first (smallest) block to ripple through plus the time taken to send the carries through each mux to the end. In a perfectly balanced square-root adder, these should be equal so neither is waiting on the other, but in practice, they are only approximately equal, so one path will genuinely be slower than the other, but not by much.
### Subtractors
Subtracting two integer numbers is generally done by taking the two's complement of the second and adding them. This can either be integrated into the adder, so that it only needs a single 'add/subtract' signal, or placed beforehand to simplify adder circuitry at the cost of adding another stage.
